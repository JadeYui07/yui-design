The Problem

As Eightpoint scaled across iOS and Android, design inconsistencies multiplied. The same UI element looked and behaved differently across platforms — not because of intentional platform customization, but because there was no shared source of truth.

Every new feature required duplicate design decisions. Engineers were interpolating missing specs. Designers were recreating components from scratch. And users were experiencing subtle inconsistencies that eroded trust in the product over time.

Audit & Discovery

Before building anything, I audited what existed — across both platforms — to understand the full scope of inconsistency and establish a baseline.

1

Visual Audit

Catalogued every unique color, typography style, spacing value, and component across iOS and Android builds. Found 47 unique button styles across the two platforms where there should have been 4.

2

Engineering Interviews

Spoke with iOS and Android engineers to understand where handoff was breaking down. Key finding: missing motion specs and unclear state definitions were the biggest time sinks.

3

Platform Guidelines Review

Reviewed Apple HIG and Material Design 3 to identify where intentional platform differences should be preserved vs. where cross-platform consistency was achievable and desirable.

4

Prioritization Workshop

Ran a cross-functional workshop to rank components by frequency of use and inconsistency severity, establishing the build order for the initial system release.

Design Process

I built the system in four layers, each one enabling the next: tokens first, then components, then documentation, then governance.

1

Design Token Architecture

Defined a three-tier token system: primitive → semantic → component. Semantic naming (color.action.primary, not color.blue.500) ensures tokens survive rebrands and theme changes without breaking components.

2

Component Library in Figma

Built 50+ components using Figma component properties, variants, and auto-layout. Each component has interactive states (default, hover, pressed, disabled, error) and a single source of truth shared across both platform files.

3

Platform Variant Strategy

Mapped every component to its iOS and Android expression — deciding case-by-case where to enforce consistency and where to honor platform convention (e.g., iOS switches vs. Android toggles).

4

Documentation & Governance

Wrote usage guidelines for every component: anatomy, do/don't examples, spacing specs, motion behavior, and accessibility requirements. Established a contribution model so the system stays alive as the product grows.

Key Design Decisions

System decisions are infrastructure decisions — they compound over time, for better or worse.

Semantic Token Naming

Tokens named by purpose, not value — color.action.primary, not color.blue.500. This means a rebrand changes one token, not 200 component overrides.

Single Figma Library, Two Platforms

One shared Figma library with platform-specific component variants, rather than two separate files. One source of truth prevents the system from forking over time.

Intentional Platform Divergence

Documented every place where iOS and Android differ by design choice (not accident). Engineers know where they have flexibility and where they don't.

Contribution Model

Built a process for product teams to propose new components — with a review gate before anything enters the system. Keeps the library authoritative, not a dumping ground.

Outcome & Metrics

The system shipped as a living library and continues to grow. Early impact was measured in handoff quality and consistency rather than user-facing metrics.

Reflection & Next Steps

The most underrated part of a design system is the governance model, not the component library. A system without a clear contribution process and an owner will drift into inconsistency within months. Getting buy-in on the process was harder — and more important — than building the components.

Next steps: connect design tokens directly to the engineering token pipeline (eliminating manual handoff entirely), expand motion specs into a dedicated motion library, and build an automated component health dashboard to surface drift before it reaches production.
